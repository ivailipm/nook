# nook

A personal household hub for one person, used on a phone in the shop and on a laptop at a desk: a grocery list linked to a promo board, a to-do list, a subscription tracker, and a Home dashboard that ties them together. Single user, but behind normal auth so it can be deployed.

## Read before you build

- `docs/nook-design/DESIGN.md`: the visual spec (fonts, colours per section, components, layout, breakpoints). Follow it exactly.
- `docs/nook-design/FEATURES.md`: what every screen does, the data model, quick-add parsing, auto-cleanup, notifications, Share Target.
- `docs/nook-design/prototype/Main.dc.html`: the click-through prototype. Read it, don't run it. Its inline styles are the exact visual values, and the JS class at the bottom (`renderVals()` and the helper methods) is the exact behaviour, including the parsers and edge cases. Where DESIGN.md and the prototype disagree, the prototype wins.
- `docs/nook-design/reference/look-and-feel.png`: the mood reference for the mobile look.
- `docs/decisions.md`: decisions that change or fill gaps in the design docs. They win over everything above.

## Stack

Laravel 13 on PHP 8.4, Livewire 4 + Alpine, Tailwind v4 (design tokens in the `@theme` block of `resources/css/app.css`; there is no `tailwind.config.js`), PostgreSQL 18, Pest 5, Larastan (level 6), Pint. Queue, cache and sessions use the database driver (no Redis). The app timezone is Europe/Brussels.

## Local setup (main checkout)

- `docker compose up -d` starts Postgres 18 on host port 5434 (databases `nook`, `nook_testing`, `nook_factory`) and Mailpit (http://localhost:8025).
- Laravel Herd serves the main checkout at http://nook.test.
- First run: `composer install && npm install && cp .env.example .env && php artisan key:generate && php artisan migrate --seed && npm run build`.
- `composer dev` runs the queue worker, the scheduler and Vite together.

## Set up a fresh checkout (factory worktrees)

With Docker running, in the worktree:

```bash
composer install --no-interaction
npm ci --no-audit --no-fund
cp .env.example .env
sed -i 's/^DB_DATABASE=nook$/DB_DATABASE=nook_factory/' .env
php artisan key:generate --no-interaction
php artisan migrate:fresh --seed --force
npm run build
```

Worktrees use the `nook_factory` database, so they never touch the main checkout's data. Factory jobs share `nook_factory` and `nook_testing`, so run one job at a time.

## Dev server on a given port

`php artisan serve --host=127.0.0.1 --port=<port>`, in the background, then open `http://127.0.0.1:<port>`. It serves the built assets in `public/build`, so run `npm run build` again after changing CSS, JS or classes in Blade. To try a file upload, add `--no-reload`: without it `artisan serve` drops `TEMP` from the server's environment, and on Windows PHP then can't store the upload ("The photo failed to upload.").

Never run `npm run dev` or `composer dev` in a factory worktree. Vite writes `public/hot`, and once Vite stops, every page asks the dead Vite server for its CSS and JS. If you find `public/hot` in a worktree, delete it.

Stop the server when you're done, by its port. Never stop processes by name: Herd runs on the same `php.exe`.

```bash
taskkill //F //PID $(netstat -ano | grep -E "127\.0\.0\.1:<port> .*LISTENING" | awk '{print $5}' | head -1)
```

That ends the listener on the port, and `artisan serve` exits with it.

The service worker runs only on secure origins: it runs on `http://127.0.0.1:<port>` but not on plain `http://nook.test` (`herd secure nook` enables it there). A registered worker and its caches stay in the browser profile, so clear them with DevTools → Application → Clear site data, or use a fresh agent-browser session. To fake having no signal, stop the dev server by its port or run `agent-browser set offline on`.

Every page except login, `/offline` and `/sw.js` is behind auth. The seeder creates the local account `ivayla@example.com` / `password` and the prototype's sample grocery items, promos, tasks and subscriptions for it (`GroceryItemSeeder`, then `PromoSeeder`, which links four of the items to promos, then `TaskSeeder`, then `SubscriptionSeeder`), only when `APP_ENV` is `local` or `testing` (factory worktrees run as `local`). Everywhere else, create the user with `php artisan nook:user`. In production, `nook:user` needs a password of at least 12 characters that hasn't appeared in a known breach (checked against Have I Been Pwned), set by `Password::defaults` in `AppServiceProvider`.

## Validation

- `composer test` runs Pint (`pint --test`), Larastan (`phpstan analyse`) and the Pest suite on Postgres (`nook_testing`; Docker must be running). All three must pass.
- `npm run build` must succeed.
- One test file: `php artisan test tests/Feature/SomeTest.php`. Format only the files you changed: `vendor/bin/pint --dirty`.
- CI (`.github/workflows/ci.yml`) runs the same checks plus a Docker image build on every pull request.

## Conventions

- Conventional commits with a scope and a one-line subject: `feat(promos): add polaroid board`, `fix(todo): keep focus after quick add`, `test(groceries): cover the quick-add parser`, `chore(ci): cache composer`.
- Logic that tests must cover (quick-add parsers, auto-linking, promo expiry, recurring rollover, monthly and yearly totals, reminder scheduling) lives in plain PHP classes under `app/`, not inside Livewire components or Blade views, and has Pest tests. Use the examples in FEATURES.md as test cases. The quick-add parsers live in `app/Parsers` (`GroceryItemParser` returns a `ParsedGroceryItem`, and `TaskParser` returns a `ParsedTask`).
- User data: each table of user data has a `user_id` foreign key (cascade on delete), and items are created and read through the user's relation (`$user->groceryItems()`). Adding a grocery item always goes through `App\Actions\AddGroceryItem` (the quick add, the add-item sheet and the promo sheet use it), which auto-links the new item to the user's active promos (moving it to the promo's store) and builds the toast message (`message()`). Given a promo as its optional last argument, it links that promo and adopts its store without searching.
- Promos: `App\Models\Promo` has the scopes `active` (`valid_until` today or later), `expired` (before today), `expiredThisWeek` (the archive: expired during this Monday-to-Sunday week) and `endingSoon` (`valid_until` from today to 3 days ahead), all worked out from today's date. `Promo::daysLeft()` counts the calendar days to `valid_until` (0 on the last day, negative once expired) and `untilLabel()` gives the polaroid label ("ends today!", "ends tomorrow", "until Sat", "expired 27 Oct"); views use these and never work out dates themselves. Every relative date in the UI goes through `App\Support\RelativeDate::format()` ("today", "tomorrow", "yesterday", the weekday for 2–6 days ahead, otherwise "10 Nov"). A promo created without a `tone` gets the next of the six polaroid tones after the user's latest promo. Photos live on the private `local` disk (`Promo::PHOTO_DISK`) and are deleted with the promo. `App\Actions\StorePromoPhoto` writes every upload as a new JPEG (longest edge 1600px, EXIF orientation applied, metadata stripped, 50 megapixels at most), and the owner-checked `promos.photo` route serves it, with views getting the URL from `Promo::photoUrl()`. `App\Actions\PinPromo` saves the add-promo form and builds its toast (`message()`). `Promo::validityLine()` gives the promo sheet's "Colruyt · valid 27 Oct – Sat" and `listItemName()` the name of the item "Add to my list" creates. Scheduled tasks live in `routes/console.php`: `nook:expire-promos` (`App\Actions\ExpirePromos`) runs daily at 00:00 to unlink items from expired promos and delete promos 30 days after their `valid_until`.
- Stores: `App\Enums\Store` is the built-in stores, and a user adds their own as `App\Models\CustomStore` rows (`$user->customStores()`, 30 characters at most). `$user->storeNames()` gives every store in chip order (the built-in ones, then the user's own oldest first, then Other), and every store chip row, the Groceries grouping by store, store validation (`Rule::in`) and the quick add's `@store` (`GroceryItemParser::parse($line, $stores)`) use it; never list `Store::cases()` in the UI. Items and promos hold the store's name as a plain string. Adding a store always goes through `App\Actions\AddStore`, which squishes and capitalises the name, refuses one the user already has (in any case) and "All", and builds its message (`message()`); removing one goes through `App\Actions\RemoveStore`, which moves its items and promos to Other. A store name can hold quotes, so pass it into a Livewire or Alpine expression with `Js::from()`.
- Tags: `App\Enums\TaskTag` is the built-in task tags, and a user adds their own as `App\Models\CustomTag` rows (`$user->customTags()`): one lower-case word, 20 characters at most, of letters, numbers, `-` and `_`. `$user->tagNames()` gives every tag in chip order (the built-in ones, then the user's own oldest first), and the To-do filter, the task sheets' Tag chips, tag validation (`Rule::in`) and the quick add's `#tag` (`TaskParser::parse($line, $tags)`, where a longer tag wins over one it starts with) use it; never list `TaskTag::cases()` in the UI. Tasks hold the tag as a plain string. Adding a tag always goes through `App\Actions\AddTag`, which drops a leading `#`, turns spaces into hyphens and lower-cases the name, refuses one the user already has and "all", and builds its message (`message()`); removing one goes through `App\Actions\RemoveTag`, which moves its tasks to home.
- Tasks: `repeat_weekday` is 0 (Sunday) to 6 and null means one-off. Ticking or unticking a task always goes through `App\Actions\ToggleTask`, which sets the state it is given (`handle($task, $done)`), leaving a task already in that state alone, then creates the next recurring task on its first tick and builds its toast (`message()`). `rolled_over` marks a task that already created its next one, so unticking and re-ticking doesn't create a second copy. Adding a task always goes through `App\Actions\CreateTask` (the quick add and the add-task sheet use it), which builds its toast (`message()`). Editing one always goes through `App\Actions\UpdateTask`, which writes only the edit form's fields (never `done`, `completed_at` or `rolled_over`), keeps a weekly task's `repeat_weekday` while its due date is unchanged and otherwise takes it from the due date (a weekly task with no date starts today), and builds its toast (`message()`). `Task::daysUntilDue()`, `isOverdue()`, `dueLabel()` ("overdue · was yesterday", "due Sat") and `repeatLabel()` ("every Thursday") give the row its meta, and `Task::homeMeta()` ("School · overdue", "Home · done") gives Home's Today card its line. `App\Support\TaskGroups::for($user, $tag)` builds the To-do groups (Overdue, Today, Upcoming, Done), and Done holds the tasks completed in the last 7 days; older ones stay in the database, off the list.
- Morning nudge: the setting is `users.morning_nudge` (default true), saved from the card on the To-do page and the bell on Home, both through `App\Actions\ToggleMorningNudge`, which builds the toast (`message()`). Nothing reads it yet.
- Subscriptions: `App\Support\SubscriptionTotals::for($user)` gives the monthly and yearly totals, the category breakdown and the savings line. Totals and the breakdown count paying subscriptions only (not cancelled, not on trial), and savings count only cancelled paid subscriptions. They go by those flags and never by dates. Cancelling a trial keeps `is_trial` true, so resuming brings it back as a live trial, and `listMeta()` words its row "trial cancelled 29 Aug · Education". Amounts stay unrounded floats until `Money::format()` prints them. `Subscription`'s wording methods (`priceLabel()`, `receiptMeta()`, `listMeta()`, `trialHeadline()`, `trialDetail()`, `reminderLabel()`) give the screen its text and say "was due" and "ended" once a date has passed; views use them and never work out dates. `comingUpLabel()` ("pays Sun 1 Nov", "trial ends Mon 2 Nov") and `comingUpAmount()` (the real charge, "€120.00", or "then €12.99") give Home's Coming up card its text. `nook:roll-subscriptions` (`App\Actions\RollSubscriptions`) runs daily at 00:00: it moves passed dates on by the cycle until they are today or later, turns unanswered trials paid in the same run, and leaves cancelled ones alone. Reading a page changes nothing. `trial_reminder` is saved from the trial card and nothing reads it yet. Adding a subscription always goes through `App\Actions\CreateSubscription`, which builds its toast (`message()`). Editing one always goes through `App\Actions\UpdateSubscription`, which writes only the edit form's fields (never `cancelled_at` or `trial_reminder`, and a past date stays as typed) and builds its toast (`message()`).
- Enums: the built-in stores, grocery categories and subscription categories are the string-backed enums `App\Enums\Store`, `App\Enums\GroceryCategory` and `App\Enums\SubscriptionCategory`, in the prototype's order, with the display name as the value. The built-in task tags, task priorities and subscription cycles are `App\Enums\TaskTag`, `App\Enums\TaskPriority` and `App\Enums\SubscriptionCycle`, whose values are the stored lower-case words rather than display names. Models cast to them, except the store and the task tag, which stay strings (see Stores and Tags). `SubscriptionCategory::swatchClass()` and `ringClass()` give a category's colours as full class names, so Tailwind finds them.
- Pages are class-based full-page Livewire components in `app/Livewire/Pages`, created with `php artisan make:livewire Pages/Name --class` (no single-file components), and render in the one layout, `resources/views/layouts/app.blade.php`, with `#[Title]` setting the page title. Routes are added with `Route::livewire()` inside the `auth` group in `routes/web.php` and named after their `App\Enums\Section` value; the enum also holds each section's labels, icon, ground, FAB label and the sheet its FAB opens. Add sheets are class-based Livewire components in `app/Livewire/Sheets` (`make:livewire Sheets/Name --class`), rendered once in `layouts/app.blade.php` so they open on every page; the add-item sheet dispatches `grocery-item-added` after saving, and the Groceries and Promo board pages refresh on it. `PromoSheet` ("The deal") opens on `show-promo` with `{ id }`; its actions recheck everything on the server and dispatch `promo-changed`, and those two pages refresh on that too. `AddPromo` ("Pin a deal") saves through `PinPromo`, then redirects to the board with a flashed toast; it resets its form when it opens, so its dates and link chips are current. `Stores` ("Your stores") opens from the dashed `<x-plus-chip>` at the end of the store chips on the Promo board and in the add-item and add-promo sheets, on top of those sheets. It adds and removes stores, says what it did in its own `role="status"` line (a toast would sit behind the open sheet), and dispatches `stores-changed`, which `Groceries`, `PromoBoard`, `Home`, `AddItem` and `AddPromo` refresh on (the two sheets fall back to Lidl when their picked store is gone), and, after adding, `store-added` with `{ name }`, which an open add-item or add-promo sheet picks. `AddTask` ("New task") dispatches `task-added` after saving, and the To-do page refreshes on it. `Tags` ("Your tags") works like `Stores` for task tags: it opens from the `<x-plus-chip>` at the end of the tag chips on To-do and in the add-task and edit-task sheets, says what it did in its status line, and dispatches `tags-changed`, which `Todo`, `Home`, `AddTask` and `TaskSheet` refresh on (the two sheets fall back to home when their picked tag is gone), and, after adding, `tag-added` with `{ name }`, which an open add-task or edit-task sheet picks. `TaskSheet` ("Edit task") opens on `show-task` with `{ id }` from the To-do rows and Home's Today rows, rechecks the task on the server, saves through `UpdateTask` or deletes the row, and dispatches `task-changed` with `{ id }` after saving or deleting; `Todo` and `Home` refresh on it and give a saved row's button its focus back. `AddSubscription` ("New subscription") saves through `CreateSubscription`, then redirects to Subscriptions with a flashed toast; it resets its form when it opens, so its date is current. `SubscriptionSheet` ("Edit subscription") opens on `show-subscription` with `{ id }` from the All subscriptions rows, rechecks the row on the server, saves through `UpdateSubscription` or deletes the row, and dispatches `subscription-changed` with `{ id }` after saving or deleting; `Subscriptions` refreshes on it and gives a saved row's button its focus back. `App\Support\HomeDashboard::for($user)` gives Home its data, with `greeting()` and `todayLine()` for its words. Both take the moment, which `Home` reads once per render and gives the view as `$now`, and `todayLine()`'s all-clear follows `greeting()`'s boundaries (morning, afternoon, evening). `Home` refreshes on `grocery-item-added`, `task-added`, `promo-changed`, `task-changed`, `stores-changed` and `tags-changed`. `App\Livewire\SidebarLinks` holds the sidebar's links, is given its section because it re-renders during Livewire requests, shows `App\Support\SidebarCounts`, and refreshes on `grocery-item-added`, `task-added` and `promo-changed` plus `nav-counts-changed`, which any new action that changes a count must dispatch. The login page and the offline page are the exceptions: plain Blade views (`resources/views/auth/login.blade.php`, which Fortify renders, and `resources/views/offline.blade.php`) in `resources/views/layouts/guest.blade.php`. In-app links use `wire:navigate` (plain, without `.hover`), and any new link must too: moving between pages swaps the page without a full reload. The layout keeps the toast, the `aria-live` announcer, the chooser and the sheets in one `@persist` block, so they stay the same elements and Livewire components from page to page, while the sidebar (with `SidebarLinks`), `<main>` and the floating nav come fresh from the server with each page. `resources/js/app.js` closes an open sheet before a navigation swaps the page, refreshes the page and `SidebarLinks` after Back or Forward (Livewire restores those from its snapshot of when you left), and writes the new page's title into the announcer. `config/livewire.php` makes the navigate progress bar peach. `AppServiceProvider` turns off Vite's preload tags, because a navigation keeps only the stylesheets and scripts in `<head>` and would add a preload tag again, fetching the CSS once more.
- Ticking: every tick checkbox (the Groceries list, To-do, and Home's Today and Groceries cards) calls `$tick` from `resources/js/ticks.js` (imported by `resources/js/app.js`, so it registers once per full page load) in its `x-on:click`, with a save function that passes only the row's numeric id and calls the `$wire` it is given, such as `$tick((done, $wire) => $wire.toggle(12, done))` (a reply can rebuild the checkbox, and Alpine's own `$wire`, looked up from a checkbox that has left the page, does nothing). `$tick` flips the checkbox's `aria-pressed` and `aria-label` (from its `data-label` and `data-checked-label`) and the row's `data-done` (on its `wire:key` element) at once, and the box, the check mark, the struck-through title and the list's grey promo badge follow those attributes through CSS, so a flipped row looks the same as one the server rendered. It saves the tapped state, one save per row at a time (a tap while a save waits only changes what the row wants, and one more save follows if the row ends up wanting the other state), through `Groceries::toggle($id, $done)`, `Todo::toggle($id, $done)`, `Home::toggleTask($id, $done)` or `Home::tickItem($id)` (tick-only with `{ tickOnly: true }`: a tap on a pressed box does nothing). It writes a waiting row's state into every re-render that lands meanwhile (Livewire's `morph` hook), so another reply can't flip it back. When a save fails (no network, an error status, 419) it flips the row back to the state the server last confirmed and toasts "That tick was not saved. Try again", without Livewire's error modal (a 419 still gets Livewire's "This page has expired" prompt), and it never retries. It returns a promise that settles once the row's saves are done, and each call site chains its focus return on it. Tick actions set state and never invert it, and stay normal Livewire actions (no `#[Async]` or `#[Renderless]`): counts, moves and toasts come with the reply's re-render. Any new tick must use `$tick`.
- PWA: `public/manifest.webmanifest` (theme and background `#190a0d`, and the share target) and the icons in `public/icons/` (`icon-192.png` and `icon-512.png`, each listed for `any` and `maskable`, so the glyph sits inside the central 80% circle, plus `apple-touch-icon.png`) are static files, linked from the `<head>` of both layouts with the `theme-color` meta. Production nginx serves `.png` as immutable for a year, so rename an icon file when its artwork changes. The service worker is `resources/js/sw.js`, which Vite never bundles: `App\Http\Controllers\ServiceWorkerController` serves it at `/sw.js` (no-cache) after two constants, `VERSION` (a short hash of `public/build/manifest.json`, `sw.js` and `resources/views/offline.blade.php`, so every build or worker change gives a new one, and nothing else does) and `PRECACHE` (`/offline` and every built file). `resources/js/pwa.js` (imported by `app.js`) registers it after `load`, behind feature checks. Three caches: `nook-shell-<version>` holds `/offline`, the built files and Livewire's script (a new version copies unchanged built files from older caches, takes over at once with `skipWaiting` and `clients.claim`, and deletes every other shell cache but the one the saved copy was taken under); `nook-groceries` holds the saved copy of `/groceries` with its version; `nook-share` holds a shared photo until the Promo board picks it up. The worker handles only same-origin GETs for `/build/assets/…` and Livewire's script (any nook cache first, then the network), page loads (navigations, through navigation preload, and `wire:navigate` fetches: the network, and the cached offline page only when the network fails), `/groceries` (the network for 4 seconds, then the saved copy, or the offline page while there is none) and `POST /promos/share`. It never touches any other request (every other POST, Livewire's updates, uploads and previews, promo photos), and online no page comes from a cache. The copy is the latest 200 `/groceries` page that wasn't redirected: a full load, a navigation, or the refetch `pwa.js` asks the worker for about 2 seconds after the last `grocery-item-added`, `promo-changed` or `nav-counts-changed`. It is saved with the stylesheets and scripts it links to, and any page response that is the login page (logging out, a lost session) deletes it, so it never reaches another user; no other user data is cached. The worker answers with the copy marked `data-offline-copy` on `<html>`, the only signal of read-only mode: the Groceries page shows its banner (`in-data-offline-copy:`), and `readOnly()` in `pwa.js` disables every button and input but the banner's "Try again", writes the banner into the announcer and turns every navigation into a full page load. `/offline` (`Route::view`, outside `auth`, in the guest layout, with no user data) is what a failed page load shows; its "Open the grocery list" link has no `wire:navigate`, because the page has no Livewire. Share target: the worker keeps the first shared photo in `nook-share` and answers with a 303 to `/promos`, so there is no server route and no CSRF exemption; whenever the Promo board shows, `pwa.js` opens the add-promo sheet, waits for its reset, puts the photo into the sheet's file input and deletes it from the cache, so it takes a picked photo's path. The login page never deletes a waiting photo, so a share made while signed out survives the login.
- Feature tests that load pages sign in first with `$this->actingAs(User::factory()->create())`.
- Reusable Blade components in `resources/views/components/`: `<x-card title variant="default|group|money" titleClass>` with an `aside` slot (`group` is the group card of Groceries and To-do: tighter padding and a 19px title; `money` is the Subscriptions card: a stronger border and background, a 20px title and no padding of its own, so callers pass it; `titleClass` adds classes to the `<h2>`, such as its colour), `<x-chip :pressed size="sm|md">`, `<x-plus-chip sheet label size="sm|md">` (the dashed + that ends a chip row the user can add to, the stores and the task tags, and opens that list's sheet; `label` is its `aria-label`; as tall as the chips beside it), `<x-checkbox :checked variant="grocery|task" size="md|sm" label checked-label>` (`sm` is the Home cards' 18px box, in the same 44px hit area; `checked-label` is the pressed state's label and defaults to `label`; its look follows its own `aria-pressed`), `<x-sheet name title>`, `<x-groceries-switch :current :list-count :promo-count>` (the List | Promo board links), `<x-field label name :gold>` (a labelled input; `type="date"` gets the date styling and `gold` the gold border), `<x-polaroid :promo :linked compact>` (a board polaroid, a button that dispatches `show-promo`; `compact` is Home's smaller one; its rotation classes are a literal map, and its tone and label colours are literal too, in `App\Support\PolaroidStyle`, which it shares with the promo sheet), `<x-promo-badge :promo variant="list|home">` (the deal on a list row, a button that dispatches `show-promo`; `list` greys inside a row with `data-done`; `home` is the soft peach one on Home, which always shows the store), `<x-link-chip href dot>` (a chip that navigates with `wire:navigate`, with no `aria-pressed`; `dot` is a full class name), `<x-subscription-avatar :subscription>` (the ringed letter), `<x-subscription-chips prefix :cycle :category>` (the Billing and Category chip groups both subscription sheets share; `prefix` keeps their label ids apart), `<x-task-chips prefix :priority :tag :tags :repeat>` (the Priority, Tag and Repeat chip groups both task sheets share; `tags` is the user's tags; `prefix` keeps their label ids apart), `<x-receipt :totals :subscriptions>` (the till receipt of the live subscriptions, with its zig-zag tear), the toast and the nav, plus anything else that repeats. A sheet opens on the `open-sheet` event and closes on the `close-sheet` event, each with `{ name }`, and the toast shows on the `toast` event with `{ message }`, dispatched from Alpine (`$dispatch`) or Livewire (`$this->dispatch('toast', message: …)`). `<x-toast>` also shows a flashed `session('toast')` once the page has loaded, for a toast that has to survive a redirect, but only after a full page load: the layout keeps the toast across `wire:navigate` (a toast that is showing finishes on the next page), so a redirect that flashes a toast must not use `navigate: true`.
- Design tokens: `text-accent`, `bg-accent` and `text-on-accent` follow the section's ground, so don't hard-code gold, apricot or peach for the accent. Fonts are `font-display` (Fraunces), `font-sans` (DM Sans, the default), `font-script` (Caveat) and `font-mono` (IBM Plex Mono).
- Icons are Lucide, rendered as `<x-lucide-…>` components with `aria-hidden="true"` (24px grid, round caps). The SVGs say `stroke-width="2"`, so give each icon the 1.75 stroke with `stroke-[1.75]`. No emoji anywhere in the UI.
- Accessibility: real `<button>`s and `<label>`s, `aria-pressed` on toggles and chips, `aria-label` on icon-only buttons, touch targets of at least 44px, the peach focus ring (2px solid `#f0b48a`, offset 2px) on everything interactive, and state never shown by colour alone.
- One codebase for a 390px phone and a laptop. The breakpoint is 900px, and `wide:` is the only responsive variant (Tailwind's default breakpoints are removed).
- Money is `€3.49`, printed by `App\Support\Money::format()`. Dates are relative when near ("today", "tomorrow", "Sat"), otherwise "10 Nov"; the long form is "Sun 1 Nov". Weeks start on Monday.
- Seeders reproduce the prototype's sample data, with dates relative to the day you seed.

## Deploy

Every merge to `main` builds `ghcr.io/ivailipm/nook` and calls Coolify's deploy webhook (skipped until the `COOLIFY_WEBHOOK` and `COOLIFY_TOKEN` repository secrets exist). `docker-compose.prod.yml` runs that image as `app` (web, migrations on start), `queue` and `scheduler`, plus Postgres. The image and CI install the `gd` and `exif` PHP extensions, which `StorePromoPhoto` needs. Don't change CI, Docker or deploy config unless the task asks for it.

## This machine

Windows. Bash is Git Bash: `php` and `composer` come from wrappers in `~/bin` that call Herd's PHP 8.4, and Python is `python` (`python3` is the Microsoft Store stub). Other projects' containers use host ports 5432, 5433, 3000, 6379, 8080 and 9200.

## Software factory

`/factory next` builds the first unchecked item in `factory/backlog.md` through spec → build → review → approve, and every job ends as a pull request into `main` that a human merges (see `.claude/skills/factory/SKILL.md`). Job state lives in `factory/jobs/` (gitignored). Dashboard: `cd factory && python -m http.server`, then open http://localhost:8000/dashboard.html.
